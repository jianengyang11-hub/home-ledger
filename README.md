# บ้านเรา · Home Ledger

บัญชีรายรับรายจ่ายของบ้าน — ภาพรวมรายเดือน, สรุปรายปี, รายการทั้งหมด, บันทึกข้อมูล
และมุมมองมือถือ รองรับภาษาไทย / ลาว ข้อมูลเก็บบน **Supabase** สองคนเห็นข้อมูลชุดเดียวกัน

## ความปลอดภัย

ล็อกอินด้วย **Supabase Auth** (อีเมล + รหัสผ่าน) รหัสผ่านตรวจที่เซิร์ฟเวอร์ ไม่มีเก็บในหน้าเว็บ
สิทธิ์บังคับด้วย **Row Level Security** ที่ฐานข้อมูล ไม่ใช่การซ่อนปุ่ม

| การกระทำ | ใครทำได้ | บังคับที่ |
| --- | --- | --- |
| อ่านรายการ | ต้องล็อกอินแล้วเท่านั้น | RLS `to authenticated` |
| เพิ่มรายการ | ในชื่อบัญชีตัวเองเท่านั้น | RLS `who = my_name()` |
| **แก้รายการ** | **ของตัวเองได้** · บัญชีหลักแก้ของทุกคนได้ | RLS `who = my_name() or is_admin()` |
| **ยกเลิกรายการ** | **บัญชีหลักเท่านั้น** | trigger `txns_guard_void` |
| **ลบถาวร** | **ไม่มีใครทำได้ผ่านเว็บ** | ไม่มี policy `delete` |
| เปลี่ยนสิทธิ์ / รหัสผ่าน | ทำได้ใน Supabase dashboard เท่านั้น | ไม่มี policy ให้เขียน `profiles` |

**คนที่ไม่ล็อกอินอ่านอะไรไม่ได้เลย** แม้จะรู้ publishable key จากโค้ดหน้าเว็บ
และถึงต้นจะเรียก API ตรงเพื่อลบรายการ ฐานข้อมูลก็ปฏิเสธ เพราะ `is_admin()` เป็น false
เช่นเดียวกับการแก้รายการของคนอื่น หรือเปลี่ยน `who` ไปเป็นชื่อคนอื่น — `with check` กันไว้แล้ว

## ประวัติการแก้ไข

ทุกครั้งที่มีการแก้รายการ ฐานข้อมูลจะบันทึกลงตาราง `txn_edits` เองด้วย **trigger**
ว่าใครแก้ เมื่อไหร่ ฟิลด์ไหน จากค่าอะไรเป็นอะไร

หน้าเว็บจะขึ้นป้าย **"แก้ไขแล้ว N×"** ที่ท้ายแถว กดแล้วแผงประวัติจะเปิดขึ้นมา:

```
ประวัติการแก้ไข · ซื้อของเข้าบ้าน โลตัส              [ปิด]
2 ก.ย. 2569 21:32   แก้โดย ปิ่น
   จำนวนเงิน   1,280 → 1,500
   หมวดหมู่     อาหาร → ของใช้ในบ้าน
1 ก.ย. 2569 16:10   แก้โดย ปิ่น
   รายการ      (ว่าง) → ซื้อของเข้าบ้าน โลตัส
   วันที่       31 ส.ค. 2569 → 01 ก.ย. 2569
```

trigger เป็นคนเขียน ไม่ใช่หน้าเว็บ และตาราง `txn_edits` **ไม่มี policy ให้ insert/update/delete เลย**
แปลว่าปลอมประวัติไม่ได้ และลบร่องรอยการแก้ของตัวเองไม่ได้ แม้จะเรียก API ตรง

| บัญชี | อีเมล | สิทธิ์ |
| --- | --- | --- |
| ปิ่น | `jianengyang11@gmail.com` | **admin** — แก้/ลบได้ |
| ต้น | `jia@gmail.com` | member — เพิ่มได้อย่างเดียว |
| บ้านเรา | `yang11@gmail.com` | member — เพิ่มได้อย่างเดียว |

เปลี่ยนอีเมลได้ที่ `config.js` และบล็อกที่ 5 ของ `schema.sql` **ต้องแก้ให้ตรงกันทั้งสองที่**
แล้วรัน `schema.sql` ใหม่

### ชื่อบัญชีตัวจริงอยู่ที่ `profiles` ที่เดียว

`txns.who` ผูก FK เข้ากับ `profiles.name` แล้ว (`upgrade_v3.sql` ข้อ 2) ใส่ชื่อมั่วไม่ได้อีก
แม้จะเรียก REST ตรง — เพราะการตรวจ FK ทำที่ฐานข้อมูลและข้าม RLS

| ทำอะไร | ผลที่ได้ |
| --- | --- |
| **เปลี่ยนชื่อใน `profiles`** | `on update cascade` — รายการเก่าทั้งหมดเปลี่ยนตามเอง ไม่มีตกค้าง |
| **ลบคนที่ยังมีรายการอยู่** | `on delete restrict` — ทำไม่ได้ รวมถึงลบ user ใน Authentication ด้วย |
| แก้ชื่อบัญชีในหน้า "ตั้งค่า" | เปลี่ยนแค่การแสดงผลบนเครื่องนั้น **แล้วจะบันทึกรายการไม่ได้** |

ช่องชื่อบัญชีในหน้าตั้งค่ายังกดแก้ได้อยู่ (เป็น local state) แต่ตอนนี้ข้อความใต้ตารางบอกตรง ๆ แล้ว
ว่าแก้แล้วบันทึกไม่ได้ ถ้าอยากให้กดแก้ไม่ได้เลย ต้องทำให้ช่องนั้นเป็น read-only — ยังไม่ได้ทำ

**เปลี่ยนชื่อใน `profiles` จะทิ้งประวัติไว้ทุกรายการ** เพราะ cascade ไปกระตุ้น trigger `txns_log_edit`
จะเห็นป้าย "แก้ไขแล้ว" ขึ้นทั้งกระดาน ระบุ `แก้โดย ?` (ทำจาก dashboard ไม่มี auth user)
เป็นพฤติกรรมที่ตั้งใจ — การเปลี่ยนชื่อคนทั้งสมุดควรมีร่องรอย ไม่ใช่เกิดขึ้นเงียบ ๆ

`void_by` กับ `txn_edits.edited_by` **ไม่ผูก FK โดยตั้งใจ** สองช่องนั้นบันทึกว่า *ตอนนั้น* ใครทำ
เป็นประวัติ ไม่ใช่เจ้าของรายการ เปลี่ยนชื่อทีหลังจึงต้องไม่ตามไปแก้

## ตั้งค่าครั้งแรก

1. **Authentication → Users → Add user → Create new user** สร้างครบ 3 คนตามอีเมลข้างบน
   ตั้งรหัสผ่านเอง และ**ติ๊ก Auto Confirm User** ทุกคน
2. **Authentication → Sign In / Providers** → ปิด **Allow new users to sign up**
   (กันคนนอกสมัครเข้ามาเอง)
3. **SQL Editor** → วางไฟล์ `schema.sql` ทั้งไฟล์ → Run
   ท้ายสุดจะแสดง 3 แถว ตรวจว่า `ปิ่น` เป็น `admin`

### ถ้าไม่เห็นป้าย "แก้ไขแล้ว" หรือขึ้น HTTP 404

แปลว่าตาราง `txn_edits` ยังไม่มีในฐานข้อมูล (ยังไม่ได้รัน `schema.sql` บล็อก 4b)
404 ตัวนี้มาจาก Supabase ไม่ใช่ GitHub Pages — เช็คได้จาก:

```powershell
curl.exe "https://xhnuigcwbcycthqjgjzb.supabase.co/rest/v1/txn_edits?select=id&limit=1" -H "apikey: <publishable key>"
```

| ผลที่ได้ | แปลว่า |
| --- | --- |
| `401 permission denied` | ตารางมีแล้ว ถูกต้อง (anon อ่านไม่ได้ตามที่ตั้งใจ) |
| `404 PGRST205 Could not find the table` | **ตารางยังไม่มี** → รัน `schema.sql` ใหม่ทั้งไฟล์ |

## ตั้งค่าที่ `config.js`

แก้ที่ไฟล์เดียว ไม่ต้องเข้าไปยุ่งกับ `Home Ledger.dc.html` ที่ยาว 140 KB

| ค่า | ใช้ที่ไหน | ถ้าไม่ใส่ |
| --- | --- | --- |
| `SUPABASE_URL` / `SUPABASE_ANON_KEY` | เชื่อมฐานข้อมูล | เว็บใช้ไม่ได้ |
| `APP_NAME` | แถบหัว · หน้าล็อกอิน · ชื่อแท็บเบราว์เซอร์ | `บ้านเรา · Home Ledger` |
| `ACCOUNTS` | ปุ่มล็อกอิน · ตัวกรอง · ปุ่มเลือกบัญชีในฟอร์ม | ชุด 3 บัญชีเริ่มต้น |
| `BUDGETS` | การ์ดงบประมาณหน้าภาพรวมรายเดือน | อาหาร / เดินทาง / บันเทิง / เป้าหมายออม |
| `YEAR_GOAL` | การ์ด "คงเหลือสะสม" หน้าสรุปรายปี | 300,000 บาท |

**`BUDGETS`** เขียนเป็น `{ cat: "ชื่อหมวด", limit: จำนวนบาท }` จะกี่บรรทัดก็ได้
`cat` ต้องสะกดตรงกับหมวดหมู่ที่ใช้บันทึกจริง ไม่งั้นจะนับได้ 0
ชื่อหมวดแปลเป็นภาษาลาวให้เองผ่านรายการหมวดหมู่ ไม่ต้องไปเพิ่มคำแปลในไฟล์ `.dc.html`

`"เป้าหมายออม"` เป็นชื่อพิเศษ — หมายถึงเงินที่เหลือเก็บ (รายรับ − รายจ่าย) ไม่ใช่หมวดรายจ่าย
และตีความกลับด้าน คือ **ใช้ไม่ถึงเป้า** ถือว่าไม่ผ่าน

**`ACCOUNTS`** เพิ่ม/ลดกี่คนก็ได้ แต่ต้องแก้ให้ตรงกัน 3 ที่เสมอ:
`config.js` → บล็อกที่ 5 ของ `schema.sql` → สร้าง user จริงใน Supabase Authentication

ถ้าใช้บัญชีเดียว **ต้องตั้ง `'admin'`** ใน `schema.sql` ไม่งั้นจะแก้หรือยกเลิกรายการไม่ได้เลย

ที่ยังตรึงในไฟล์ `.dc.html`: ข้อความหน้าล็อกอิน (`t_hero1` / `t_hero2`) เพราะมีสองภาษา,
คำแปลลาวของ role ที่รู้จักแค่ `pin`/`ton`/`home` (id อื่นได้ข้อความไทยแทน ไม่ error),
และ `<title>` ใน `index.html` ซึ่งเป็นหน้า redirect ชั่วขณะ

## มือถือ

ใช้บนมือถือได้เต็มรูปแบบ ไม่ต้องซูม ไม่มีการเลื่อนซ้าย-ขวาทั้งหน้า
ทดสอบผ่านที่ความกว้าง 320 / 360 / 390 / 768 px ครบทุกหน้าจอ

จุดที่ปรับตามขนาดจอ (อยู่ในบล็อก `@media` ท้าย `<style>` ของไฟล์ `.dc.html`):

| ที่ | บนมือถือ |
| --- | --- |
| หน้า login | ซ้อนบน-ล่าง แทนการแบ่งซ้าย-ขวา |
| แถบหัว | ซ่อนโลโก้ · แท็บเลื่อนแนวนอนได้ |
| การ์ด KPI | 4 ช่อง → 2 ช่อง → 1 ช่อง (ตามความกว้าง) |
| ตารางรายการ | เลื่อนแนวนอนในกรอบตัวเอง ไม่ดันทั้งหน้า |
| กราฟ 12 เดือน | บีบช่องไฟและชื่อเดือน |
| ฟอร์มบันทึก | เรียงคอลัมน์เดียว |

สไตล์ในไฟล์เป็น inline ทั้งหมด กฎใน `@media` จึงต้องใช้ `!important` เพื่อทับ
และใช้คลาส `hl-*` เป็นตัวจับ — ถ้าแก้เลย์เอาต์เพิ่ม อย่าลบคลาสพวกนี้ทิ้ง

### หน้า "มือถือ" เป็นภาพตัวอย่าง ไม่ใช่แอปมือถือ

ใช้งานจริงคือ**เปิดเว็บนี้บนมือถือได้เลย** หน้าปกติรองรับจอเล็กอยู่แล้วตามตารางข้างบน
หน้า "มือถือ" เป็นหน้าโชว์การออกแบบ มีป้ายบอกไว้ใต้หัวข้อแล้วว่ากดใช้งานจากหน้านี้ไม่ได้

เครื่องกลาง ("ภาพรวมเดือน") ใช้ตัวเลขจริง ส่วนเครื่องซ้ายกับขวาเป็นภาพนิ่ง

**เครื่องซ้ายต้องสะท้อนวิธีล็อกอินจริงเสมอ** เดิมวาดเป็นแป้น PIN 6 หลัก ซึ่งเป็นของเหลือจาก
เวอร์ชันก่อนเปลี่ยนมาใช้ Supabase Auth — กดไม่ได้อยู่แล้วเพราะเป็นภาพ แต่ที่แย่กว่าคือ
มัน**บอกวิธีเข้าระบบผิดไปเลย** ตอนนี้เปลี่ยนเป็นรายชื่อบัญชี + ช่องรหัสผ่านให้ตรงกับของจริง
(รายชื่อดึงจาก `ACCOUNTS` ใน `config.js` ชุดเดียวกับหน้าล็อกอินจริง จึงเพี้ยนตามกันไม่ได้)

ในโค้ดยังเหลือชื่อจากยุค PIN อยู่บ้าง เช่น `pinErr`, `t_enterPin`, `t_of6` — เป็นแค่ชื่อตัวแปร
ค่าข้างในถูกต้องแล้ว ถ้าจะเปลี่ยนชื่อให้ตรงความหมายก็ทำได้ แต่ไม่ได้กระทบการทำงาน

## ประเภทรายการ

| ประเภท | ทำอะไร | นับในรายรับ/รายจ่าย | นับในยอดคงเหลือ |
| --- | --- | --- | --- |
| รายรับ | เงินเข้าช่องทาง | ✓ | ✓ |
| รายจ่าย | เงินออกจากช่องทาง | ✓ | ✓ |
| **โอนระหว่างช่องทาง** | ย้ายจาก `method` → `method_to` | ✗ | ✓ (ย้ายที่เฉย ๆ) |
| **ยอดยกมา** | เงินตั้งต้นก่อนเริ่มใช้สมุด | ✗ | ✓ |

โอนใช้กับ **ถอน ATM** (โอน → เงินสด) และ **จ่ายบัตร** (โอน → บัตร)
ถ้าไม่มีประเภทนี้ ยอดแยกช่องทางจะเพี้ยนทันทีที่ถอนเงิน

### ค่าที่เก็บลงฐานข้อมูลต้องเป็นภาษาไทยเสมอ

`method`, `method_to`, `cat`, `kind` เก็บเป็น**ค่ามาตรฐานชุดเดียว** ส่วนภาษาลาวเป็นแค่ป้ายที่แสดง
สลับภาษาแล้วต้องได้ค่าเดิมลงฐานข้อมูล ไม่งั้นสองคนบันทึกคนละภาษาจะกลายเป็นคนละช่องทาง

เคยพลาดตรงนี้มาแล้วที่ปุ่มเลือก **ช่องทางจ่าย** ในหน้าบันทึกข้อมูล — เก็บป้ายที่แสดงลงไปตรง ๆ
บันทึกด้วยภาษาลาวจึงได้ `ເງິນສົດ` ซึ่งไม่ตรงกับ `METHODS[0]` แล้วแถวนั้น**หลุดจากการ์ด
ยอดคงเหลือทุกใบเงียบ ๆ** (`balOf()` จับคู่ด้วยค่าตรงตัว) และนับเป็นคนละช่องทางกับที่บันทึกเป็นไทย

**ถ้าเคยบันทึกด้วยภาษาลาวก่อนหน้านี้ ข้อมูลเก่ายังผิดอยู่** ตรวจและแก้ได้ด้วย:

```sql
-- ตรวจก่อน — ควรได้ 0 แถว
select method, count(*) from public.txns
 where method not in ('เงินสด','โอน','บัตร') group by method;

-- ถ้าเจอ ค่อยแก้
update public.txns set method = case method
         when 'ເງິນສົດ' then 'เงินสด' when 'ໂອນ' then 'โอน' when 'ບັດ' then 'บัตร' end
 where method in ('ເງິນສົດ','ໂອນ','ບັດ');
```

ถ้า `update` ขึ้น `23505 txns_opening_unique` แปลว่าช่องทางนั้นมียอดยกมาทั้งฉบับไทยและฉบับลาว
พอรวมเป็นช่องทางเดียวกันจึงซ้ำ — ไปยกเลิกอันใดอันหนึ่งก่อน แล้วรัน `update` ใหม่
`method_to` ไม่ต้องแก้ ปุ่มนั้นเก็บค่ามาตรฐานถูกมาตั้งแต่แรก

## ยอดคงเหลือแยกช่องทาง

การ์ด 3 ใบบนหน้าภาพรวมรายเดือน — **สะสมตั้งแต่รายการแรกถึงวันนี้** ไม่รีเซ็ตรายเดือน

| การ์ด | สูตร |
| --- | --- |
| เงินสดคงเหลือ | ยอดยกมา + รับ − จ่าย + โอนเข้า − โอนออก ของ `เงินสด` |
| เงินในบัญชี | เหมือนกัน แต่ของ `โอน` |
| **ยอดค้างบัตร** | รายจ่ายบัตร − เงินที่โอนไปจ่ายบัตร → **เป็นหนี้ ไม่ใช่เงินคงเหลือ** |

**ถ้ายังไม่ได้ใส่ยอดยกมา** การ์ดจะขึ้นคำเตือนไว้ ว่าตัวเลขนี้เป็นยอดตั้งแต่วันแรกที่บันทึก
ไม่ใช่เงินจริงในกระเป๋า — ใส่ยอดยกมาครั้งเดียวต่อช่องทาง แล้วตัวเลขจะตรงกับความจริง

**นับถึงวันนี้จริง ๆ — รายการที่ลงวันไว้ล่วงหน้าไม่ถูกนับ** เพราะเงินยังไม่เข้าออกจริง
เดิมการ์ดนับทุกแถวไม่ดูวันที่เลย ทั้งที่ป้ายเขียนว่า "สะสมจากยอดยกมาถึงวันนี้"
เจอง่ายกว่าที่คิด เพราะ `run_recurring()` สร้างรายการประจำของเดือนนี้ให้ตั้งแต่ตอนล็อกอิน
ถ้าแม่แบบเป็นวันที่ 25 แต่วันนี้วันที่ 3 เงินจะหายไปทั้งก้อนตั้งแต่ต้นเดือน

ถ้ามีรายการล่วงหน้าค้างอยู่ การ์ดจะบอกไว้ข้างล่างว่ามีกี่รายการที่ยังไม่ถูกนับ — ตัดได้ แต่ไม่ตัดเงียบ ๆ

### ยอดยกมาใส่ซ้ำไม่ได้

ยอดยกมาที่ใส่ซ้ำจะบวกเข้ายอดคงเหลือทุกครั้ง ได้ตัวเลขที่ดูปกติแต่ผิด และไม่มีอะไรฟ้อง
ฐานข้อมูลจึงบังคับว่า **หนึ่ง (บัญชี · ช่องทาง · สกุลเงิน) มียอดยกมาที่ใช้อยู่ได้แถวเดียว**
ด้วย partial unique index `txns_opening_unique` ใน `upgrade_v3.sql` ข้อ 1

แยกตามสกุลเงินด้วย เพราะช่องทางเดียวอาจมีเงินสองสกุล และระบบนี้ไม่แปลงค่าข้ามสกุล
นับเฉพาะแถวที่ยังไม่ถูกยกเลิก — **ยกเลิกแถวเก่าแล้วใส่ใหม่ได้ตามปกติ** ประวัติยังอยู่ครบ

| ที่ไหน | เจออะไร |
| --- | --- |
| หน้าบันทึกข้อมูล | เช็กก่อนยิง ขึ้นข้อความพร้อม**ยอดเดิม**ที่มีอยู่ ให้กดแก้แทน |
| ฐานข้อมูล | `HTTP 409` · เรียก REST ตรงก็ใส่ซ้ำไม่ได้ กันไว้อีกชั้นเผื่อสองคนใส่พร้อมกัน |
| กดกู้คืน | ถ้าช่องทางนั้นมีแถวใหม่ไปแล้ว กู้คืนไม่ได้ ขึ้นแบนเนอร์แดงบนสุดบอกเหตุผล |

ถ้าตารางผลลัพธ์ของ `upgrade_v3.sql` ขึ้น **"มียอดยกมาซ้ำค้างอยู่ก่อนแล้ว"** แปลว่ามีของซ้ำ
อยู่ในฐานข้อมูลตั้งแต่ก่อนมีกฎนี้ ช่อง "ต้องทำอะไรต่อ" จะไล่ให้ว่าซ้ำที่บัญชี/ช่องทางไหน `id` อะไรบ้าง
ไปกดยกเลิกแถวที่เกินให้เหลือช่องทางละแถว แล้วรันไฟล์ใหม่ — ไฟล์นี้ไม่ลบข้อมูลให้เอง

## แนบสลิป

ไฟล์อยู่ใน **Supabase Storage** ถัง `slips` ส่วนฐานข้อมูลเก็บแค่ที่อยู่ไฟล์ในคอลัมน์ `txns.slip`
รับ JPG / PNG / PDF ไม่เกิน 5 MB — บังคับทั้งที่หน้าเว็บ (เพื่อบอกเป็นภาษาคน) และที่ตัวถัง

| กฎ | ทำไม |
| --- | --- |
| **ถังไม่เปิดสาธารณะ** | สลิปมีเลขบัญชี ยอดเงิน ชื่อคน ถ้าเปิดสาธารณะใครเดา URL ถูกก็เปิดดูได้ |
| หน้าเว็บขอ**ลิงก์ชั่วคราว**อายุ 1 ชม. ทุกครั้งที่กดเปิดดู | ไม่มีลิงก์ถาวรให้หลุด |
| **ทับไฟล์เดิมไม่ได้ ลบไม่ได้** (ไม่มี policy `update`/`delete`) | หลักการเดียวกับ `txn_edits` — ลบสลิปได้ก็ลบหลักฐานได้ |
| เปลี่ยนสลิป = อัปไฟล์ใหม่แล้วชี้ไปไฟล์ใหม่ | ไฟล์เก่ายังอยู่ และ trigger บันทึกไว้ว่าเปลี่ยนเมื่อไหร่ โดยใคร |

**อัปโหลดก่อนบันทึกแถวเสมอ** ถ้าอัปไม่ผ่านก็ไม่บันทึกแถว จะได้ไม่มีรายการที่อ้างไฟล์ที่ไม่มีอยู่

### ยังไม่ได้รัน `upgrade_v4.sql` ก็ต้องใช้งานส่วนอื่นได้ตามปกติ

หลักเดียวกับตาราง `cats` — **ของเสริมใช้ไม่ได้ ต้องไม่ลากของหลักพังไปด้วย**

ตอนโหลด หน้าเว็บยิง `select=slip&limit=1` ถามฐานข้อมูลว่ามีคอลัมน์นี้หรือยัง (ได้ `400` = ยังไม่มี)
แล้วเก็บไว้ใน `slipLive` ถ้ายังไม่มี กล่องแนบสลิปจะกดไม่ได้และขึ้นว่าต้องรัน `upgrade_v4.sql` ก่อน

และ **ส่งช่อง `slip` ไปเฉพาะตอนมีไฟล์ใหม่จริง ๆ เท่านั้น** ห้ามส่ง `slip: ""` ติดไปกับทุกการบันทึก
เพราะถ้ายังไม่มีคอลัมน์ ฐานข้อมูลจะตีกลับ `400` แล้ว**บันทึกไม่ได้เลยแม้แต่รายการที่ไม่มีสลิป**
(เขียนพลาดแบบนี้มาแล้วรอบหนึ่ง จับได้ตอนไล่ตรวจ ไม่ใช่ตอนใช้งาน)

ถ้าคอลัมน์มีแล้วแต่ถังหรือสิทธิ์ยังไม่พร้อม ข้อความจะบอกตรง ๆ ว่าติดข้อไหนของ `upgrade_v4.sql`
และย้ำว่า **"รายการยังไม่ถูกบันทึก"** จะได้ไม่เข้าใจผิดว่าบันทึกไปแล้วแต่สลิปหาย
ตั้งชื่อไฟล์แบบสุ่มเพราะตอนอัปยังไม่มี `id` ของรายการ แยกโฟลเดอร์ตามเดือนไว้ให้หาง่าย

ในหน้ารายการทั้งหมด แถวที่แนบไว้จะมีปุ่ม **สลิป** กดแล้วเปิดแท็บใหม่
(เปิดแท็บตั้งแต่ตอนกดก่อนไปขอลิงก์ ไม่งั้นเบราว์เซอร์จะมองว่าเป็น popup แล้วบล็อกทิ้ง)

**ข้อแลกเปลี่ยนที่ยอมรับไว้:** ไฟล์ที่ถูกแทนที่แล้วจะค้างอยู่ในถังโดยไม่มีใครชี้ถึง
กินพื้นที่ไปเรื่อย ๆ ถ้าอยากเก็บกวาดต้องเข้าไปลบเองที่ Storage ใน dashboard

## ยกเลิกรายการ แทนการลบทิ้ง

ลบถาวรถูกปิดไปแล้ว (ไม่มี policy `delete`) เพราะ `txn_edits` ผูกด้วย `on delete cascade`
ลบรายการทีเดียว **ประวัติการแก้ไขทั้งหมดของรายการนั้นหายตามไปด้วย** ซึ่งขัดกับที่ตั้งใจไว้

แทนที่ด้วยการยกเลิก: แถวยังอยู่ ไม่นับในยอดรวมไหนเลย ในหน้ารายการจะขีดฆ่าและจางลง
พร้อมป้าย "ยกเลิกโดย ปิ่น · 3 ก.ย. 2569 14:22 · บันทึกซ้ำ" กดปุ่ม **กู้คืน** กลับมาได้

**ต้องระบุเหตุผลทุกครั้ง** กดปุ่ม *ยกเลิก* แล้วแผงกรอกเหตุผลจะเปิดขึ้นใต้ตาราง
เหตุผลว่างจะยกเลิกไม่ได้ — ฐานข้อมูลปฏิเสธเองด้วย ไม่ใช่แค่หน้าเว็บกัน

`void_at` / `void_by` หน้าเว็บกำหนดเองไม่ได้ — trigger `txns_guard_void` เขียนทับด้วย `now()`
กับ `my_name()` เสมอ ปฏิเสธถ้าคนกดไม่ใช่ `is_admin()` และถ้าไม่ได้ยกเลิกหรือกู้คืนจริง
ก็แก้ `void_by` / `void_reason` ไม่ได้เลย — ปลอมเหตุผลย้อนหลังไม่ได้

## หมวดหมู่

เก็บในตาราง `cats` ในฐานข้อมูล **ทุกคนเห็นชุดเดียวกัน** แก้ได้เฉพาะบัญชีหลัก
พิมพ์แล้วเห็นทันที บันทึกให้เองหลังหยุดพิมพ์ 0.6 วินาที
ถ้าฐานข้อมูลไม่รับ (ไม่ใช่ admin / ตารางยังไม่มี) จะโหลดของจริงกลับมาทับ ไม่หลอกตาว่าแก้สำเร็จ

*ก่อนหน้านี้หมวดหมู่อยู่ในหน้าเว็บล้วน ๆ กดเพิ่มได้ แต่รีเฟรชแล้วหาย และอีกคนไม่เคยเห็น*

## รายการประจำ

ติดธง "ประจำ" แล้วระบบจะสร้างซ้ำให้ทุกเดือน **วันเดียวกับรายการต้นแบบ**
เดือนที่สั้นกว่า (ตั้งวันที่ 31 แต่เดือนนั้นมี 30 วัน) จะใช้วันสุดท้ายของเดือนแทน

ทำงานด้วยฟังก์ชัน `run_recurring()` ในฐานข้อมูล หน้าเว็บเรียกให้เองทุกครั้งที่ล็อกอิน
ไม่ได้เปิดแอปหลายเดือนก็ไล่เติมย้อนหลังให้ครบ และกันสร้างซ้ำในเดือนเดียวกันไว้แล้ว

ไม่ได้ใช้ `pg_cron` เพื่อไม่ต้องพึ่ง extension — ถ้าอยากให้เดินเองโดยไม่ต้องเปิดแอป
เอาฟังก์ชันเดิมไปตั้ง `cron.schedule` ได้เลย

*ก่อนหน้านี้ธง "ประจำ" เป็นแค่ป้ายข้อความ ไม่มีอะไรสร้างรายการซ้ำเลย ทั้งที่หน้าเว็บบอกว่าจะสร้างให้*

## เรื่องสกุลเงิน

**ระบบนี้ไม่มีอัตราแลกเปลี่ยน** และจะไม่มี — เป็นการตัดสินใจ ไม่ใช่ของที่ยังไม่ได้ทำ

เรตที่ฝังไว้ในโค้ดจะเก่าลงทุกวัน แล้วทำให้ทุกตัวเลขที่ผ่านการแปลงค่าผิดไปเรื่อย ๆ
โดยไม่มีอะไรฟ้อง ยอดที่ดูน่าเชื่อแต่ผิด แย่กว่ายอดที่บอกตรง ๆ ว่าคนละสกุล

| ที่ไหน | ทำอย่างไร |
| --- | --- |
| รายการทั้งหมด · ยอดรวมท้ายตาราง | แยกทุกสกุลในบรรทัดเดียว `₭2,300,000 · ฿12,400` |
| แต่ละแถว | แสดงด้วยสกุลของแถวนั้นเอง |
| **ภาพรวมรายเดือน · สรุปรายปี** | **คิดทีละสกุล** — มีปุ่มเลือกสกุลอยู่บนหน้า |

หน้าที่มีกราฟกับ % ต้องมีฐานเดียวกันถึงจะเทียบกันได้ จึงกรองเหลือสกุลเดียวแทนการแปลงค่า
ปุ่มเลือกสกุลตั้งต้นเป็นสกุลของบัญชีที่ล็อกอิน และบอกไว้ข้าง ๆ ว่ามีอีกกี่รายการที่ไม่ถูกนับ

**ทุกที่ที่กรองสกุลทิ้ง ต้องบอกจำนวนที่ตัดออก** — ตัดได้ แต่ห้ามตัดเงียบ ๆ ตรงนี้เคยหลุด 2 จุด:

| หน้า | เดิม | ตอนนี้ |
| --- | --- | --- |
| ภาพรวมรายเดือน | บอกอยู่แล้ว | นับเฉพาะเดือนที่กำลังดู |
| **สรุปรายปี** | **ไม่บอกเลย** | นับทั้งปีที่กำลังดู (คนละช่วงกับหน้าเดือน ใช้ตัวเลขร่วมกันไม่ได้) |
| **รายการทั้งหมด** | **ไม่บอกเลย** | บอกว่าแถบแยกหมวดคิดสกุลเดียว ส่วนยอดรวมหัวการ์ดรวมทุกสกุล |

จุดสุดท้ายคือที่สับสนที่สุด — การ์ด "รายรับ · แยกตามหมวด" มียอดรวมหลายสกุลอยู่ที่หัว
(`₭2,300,000 · ฿12,400`) แต่แถบ % ข้างล่างคิดได้ทีละสกุล แถบจึงรวมกันไม่เท่าหัวการ์ด
ทั้งสองค่าถูกทั้งคู่ แค่คนละฐาน ตอนนี้มีบรรทัดบอกไว้แล้วว่าทำไม

งบประมาณกับเป้าหมายรายปีใน `config.js` ผูกกับ `code` ของตัวเอง
จะแสดงเฉพาะตอนที่กำลังดูสกุลเดียวกัน ไม่มีการแปลงค่ามาเทียบ

เพิ่ม/ลดสกุลเงินได้ที่ `CURRENCIES` ใน `config.js`

## การโหลดข้อมูล

หน้าเว็บคิดยอดทุกอย่างจากรายการทั้งหมดในเครื่องผู้ใช้ ไม่ได้ให้ฐานข้อมูลสรุปมาให้
เพราะยอดคงเหลือแยกช่องทางเป็นยอด**สะสมตั้งแต่รายการแรก** ไม่ใช่ยอดของเดือนที่กำลังดู

ตรงนี้เคยเป็นกับดัก — `DB.list()` กับ `DB.edits()` ยิงขอทีเดียวไม่ใส่ `limit`
แต่ **PostgREST ตัดผลลัพธ์ที่เพดาน Max rows ของโปรเจกต์** (ค่าเริ่มต้นของ Supabase คือ 1,000)
และตัดแบบเงียบ ๆ ตอบ `200 OK` เหมือนได้ครบ พอรายการเกินพันเมื่อไหร่
ยอดรวม ยอดคงเหลือ และกราฟจะขาดหายทันที **โดยไม่มีอะไรฟ้องสักตัว**

ตอนนี้ทั้งสองตัวเรียกผ่าน `listAll()` ที่วนขอทีละ 1,000 แถวจนกว่าจะได้หน้าว่าง
`offset` นับจากจำนวนที่ได้มาแล้วจริง ไม่ใช่ขนาดหน้าที่ขอไป — ถ้าเพดานฝั่งเซิร์ฟเวอร์
ถูกตั้งไว้ต่ำกว่าที่ขอ ก็ยังไล่เก็บได้ครบอยู่ดี ไม่ต้องไปเดาว่าเพดานจริงเท่าไหร่

จึงมีการยิงเกินมา 1 ครั้งเสมอ (ครั้งสุดท้ายที่ได้หน้าว่างกลับมา) แลกกับการไม่ต้องเชื่อค่า config
ที่ฝั่งเว็บมองไม่เห็น — ที่ขนาดข้อมูลระดับบัญชีบ้าน คือ 2 request ต่อการโหลดหนึ่งครั้ง

ลำดับที่ขอต้องนิ่งข้ามหน้า ไม่งั้นแถวจะซ้ำหรือหายตรงรอยต่อ ทั้งสองตัวจึงปิดท้ายด้วย `id`
ที่ไม่ซ้ำเสมอ (`order=ts.desc,id.desc` และ `order=edited_at.desc,id.desc`)

## การเข้าสู่ระบบและ session

ล็อกอินแล้วเก็บ `access_token` + `refresh_token` ไว้ใน `localStorage` เปิดใหม่จึงไม่ต้องล็อกอินซ้ำ
`call()` ดูวันหมดอายุก่อนยิงทุกครั้ง หมดอายุแล้วก็ต่ออายุให้เอง และเจอ `401` ก็ลองใหม่อีกหนึ่งครั้ง

**ต่ออายุได้ทีละสายเท่านั้น** — `refresh_token` ของ Supabase ใช้แล้วหมุนตัวใหม่ทันที
แต่ `load()` ยิง `list` / `edits` / `cats` พร้อมกัน 3 สาย และ `listAll()` ยังยิงซ้ำอีกหลายหน้า
ถ้า token หมดอายุพอดี ทุกสายจะแย่งกันต่ออายุด้วย `refresh_token` ตัวเดียวกัน
สายที่ช้าจะถือ token ที่ถูกหมุนทิ้งไปแล้ว แล้ว**เด้งออกจากระบบทั้งที่เพิ่งต่ออายุสำเร็จ**

`AUTH.refresh()` จึงรวมเป็นสายเดียว ใครมาทีหลังรอผลของสายแรก และประหยัด request ไปในตัว

จุดที่พลาดง่าย: ต้องปลดล็อกใน `finally` **ข้างใน** ฟังก์ชัน ไม่ใช่ต่อ `.then()` ไว้ข้างนอก
เพราะ `.then()` ทำงานช้าไปหนึ่ง microtask คนที่เรียกซ้ำทันทีหลัง `await` จะได้ promise
ตัวเก่าที่จบไปแล้วคืนไปโดยไม่ได้ต่ออายุจริง — เขียนแบบผิดครั้งแรกและจับได้ตอนเขียนเทสต์
